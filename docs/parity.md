# AWX parity

Feature by feature comparison of awxnext with AWX 24.6, the last AWX release,
from an audit of the code on 2026-10-27 (not of the docs). Status words:

- **Done**: works as in AWX, possibly with a different implementation.
- **Partial**: present, with the gap in the notes.
- **Missing**: not there, and not ruled out by the plan.
- **Later** / **By design**: deferred or excluded by [PLAN.md](PLAN.md).

## Where it stands

The core of AWX is there and tested end to end: the `/api/v2` resource model
with AWX's filtering, OPTIONS metadata and object roles; inventories (regular,
smart, constructed) and cloud inventory sources; credentials with custom types
and every AWX secret lookup; git projects; job templates with every
launch prompt, surveys, slicing, callbacks and webhooks; ad hoc commands;
workflows with approvals and convergence; schedules; management jobs; remote
execution nodes and Kubernetes container groups; HA on PostgreSQL alone.

The gaps fall in four groups:

1. **Settings that do nothing** (fixed in roadmap M1, 2026-10-28). Every
   setting now has an effect, or says "No effect in awxnext" and why in its
   help (analytics, subscriptions, OAuth2, custom virtualenvs, and
   `LOG_AGGREGATOR_*` until M6-03). A test fails CI when a setting is neither.
2. **API endpoints that AWX clients call**: done (the bulk API, the
   dashboard, host metrics, the subscription endpoints and instance health
   checks, roadmap M2-02 to M2-06).
   Compatibility with the collection, awxkit and the Terraform provider is
   tested nightly since roadmap M2-01 ([compat/](../compat/README.md)); the
   gaps those suites found are roadmap M2-14 to M2-26.
3. **Deferred by plan**: RADIUS and TACACS+ login (LDAP, SAML, GitHub, Google and Azure AD are done, roadmap M5-02 to M5-05);
   notification types other than email, webhook and Slack (Slack, and a
   Teams type of awxnext's own, are roadmap M11)
   (backup and restore, and the Helm chart, are done, roadmap M6-09 and M6-10; CyberArk, Thycotic, AWS Secrets Manager and Centrify lookups are done,
   roadmap M4-07; archive projects, roadmap M4-10).
4. **UI holes over a finished API**: a few, listed below (inventory instance
   groups, inventory source schedules, `start_at_task` and credential type
   management are done, roadmap M7-01 to M7-04).

## Fixed during the audit

| Bug | Fix |
|---|---|
| Fact cache silently broken with ansible-core 2.19+ execution environments (new `s1_<host>` / `__payload__` format) | Both formats are seeded and read; only facts a run changed are saved |
| Copying a workflow shared its approval templates with the original, so editing one renamed both | A copy gets its own approval templates |
| `PATCH users/N/` with `password: "$encrypted$"` (what reads return) set that literal password | The placeholder keeps the current password |
| Editing a deactivated user in the UI reactivated them (`is_active` was not serialized) | `is_active` is returned |
| Users from OIDC showed as local accounts with password fields | `external_account` and `auth` reflect the identity provider |
| Management jobs were offered as workflow steps in the UI but rejected by the API | Management-job nodes run, with `days`/`dry_run` from the node |
| The template page showed `/generic/` as the generic webhook URL | Shows `/webhook/` |
| The template list could not tell which templates the user may edit or copy (no capabilities on `unified_job_templates`) | Each row carries its template's own capabilities |
| `unified_job_templates` rows lacked their template's own fields (`related.launch`, `ask_*_on_launch`), so ansible-rulebook's `run_job_template` could not launch one | Each row holds what its template's own endpoint shows, as in AWX |

A GitHub user is one account across GitHub's three logins (and across Enterprise's), found by GitHub's user ID. The importer keeps AWX's GitHub users GitHub users. Deliberate difference: an email already used by another account refuses the login instead of linking to that account (AWX's `associate_by_email` would log the GitHub user in as it) |
| Google and Azure AD login | Yes | Done | Roadmap M5-05. AWX's `SOCIAL_AUTH_GOOGLE_OAUTH2_*` and `SOCIAL_AUTH_AZUREAD_OAUTH2_*` settings, so imported AWX settings work without editing: the same callback URLs (`/sso/complete/google-oauth2/`, `/sso/complete/azuread-oauth2/`), read-only from `TOWER_URL_BASE`. python-social-auth's backends: Google with AWX's `profile` scope and the backend's `openid email profile`, `AUTH_EXTRA_ARGUMENTS` (such as `hd`), the userinfo endpoint, the email as the user ID and its local part as the username, `WHITELISTED_DOMAINS` ("Your credentials aren't allowed"); Azure AD (`common` tenant, v1 endpoints, `openid profile user_impersonation email`) with the ID token's claims, the `upn` as the user ID and the email when there is none, the name as the username. ## Projects, jobs and workflows

|---|---|---|---|
| Git and manual projects | Yes | Done | Native Go sync, one immutable checkout per commit. - Computed questions and secret outputs (roadmap M15-03): a survey question with `value_from` is never asked; the server computes it at launch with an expr expression over the item picked in an earlier list (`item("vlan").gateway`), the earlier answers, the user, their team and the portal request (`request.id`, `request.expires_at`), and refuses a launch, schedule, request or catalog item that sets it; `password(n)` generates a password, encrypted and masked like a survey password; a job template's `string` output can be `secret`: removed from the `set_stats` events, masked in the output after them, stored encrypted, shown as `$encrypted$`, and passed to the next workflow nodes as a survey password ([Computed questions](surveys.md#computed-questions-value_from), [Secret outputs](workflows.md#secret-outputs)). AWX asks every survey question and keeps artifacts in clear.
- Approvals of requests (roadmap M15-04): a catalog item's `approval_rules`, each an expr condition on the answers, the team and the kind of request, with its approvers (the request's Team Admins, a team, or the users that a picked item names, by username or email) and how many approvals it needs; every rule that holds gets a workflow approval, in parallel, and the first deny (which needs a comment) or timeout denies the request; nobody approves their own request, the organization's admins approve when nobody else is left and may answer any waiting request, which the activity stream records; maintenance windows and change freezes list items, whose requests they refuse or hold for an exception that the item's team approves; an item's email notification template mails the approvers and the requester at their own addresses ([Approvals](operations.md#approvals)). AWX's approvals are workflow nodes with one approver.
- Deployments and day-2 actions (roadmap M15-05): a `deployment` item's successful request records a deployment, owned by the requester and the request's team, with the declared outputs of its run (secret ones encrypted); the item lays out how to connect with expr values over the outputs, or lists every output, and showing a secret entry is for the owners only and logged; day-2 actions run the item's templates with the outputs, through the item's rules, and update them; a deployment is handed over to a user or team that can request the item, who is mailed; deleting it runs the item's teardown, and a failed teardown flags it with what was left ([Deployments](operations.md#deployments)). AWX has no deployments.
- Deployment lifetimes (roadmap M15-06): a deployment expires when its requester chose, up to the item's longest lifetime; its owners extend it by the item's steps, as requests of kind `extend` that the item's rules may hold for approval, within caps on the number of extensions and the whole lifetime, past which the item's admins set the expiry; reminders 24 and 2 hours before expiry mail the owners and go to the item's reminder notification templates (email, webhook), with a link to the deployment; at expiry its teardown runs, inside a change freeze too unless the item says otherwise ([Lifetime](operations.md#lifetime)). AWX has no deployments.
- Catalog quotas (roadmap M15-07): an item limits the deployments each team, or each user requesting for no team, keeps at once and the requests they make in 24 hours; a deployment whose teardown failed keeps its place, a failed provisioning frees it; over quota, a request is refused with the reason or waits for the item's owner team, as the item says; the request form shows what's left, a hand-over needs room in the new owner's quota, and the item's admins see the usage through the API and on the Catalog quotas page ([Quotas](operations.md#quotas)). AWX has no quotas.
- Self-service portal (roadmap M15-08): `/portal` in the same UI, with a top bar of its own and no admin navigation, phone first; users with only request roles land there, others reach it from the account menu and go back through Admin view; an organization's `portal_title` and `portal_logo`; the catalog by category with a search, a frozen item's freeze, and what needs the user (their open requests, deployments expiring within 3 days, approvals to give) from `/api/v2/portal/`; the item's form previews the approvals it will need and why, the quota left and the expiry (`POST catalog_items/N/preview/`); My requests shows each request's steps and what happens next, and the run's plays, reworded by the item's `step_labels`, with a percentage from the last successful run's task count and the job for those who can see it (`catalog_requests/N/progress/`) ([The portal](operations.md#the-portal)). AWX has no portal.
- Deployments and approvals in the portal (roadmap M15-09): My deployments shows each deployment's lifetime as a cell per day (gone, today, left, added by extensions) with the item's extensions and who approves them, how to connect with copy buttons and secrets shown on demand and logged, its actions with their surveys, its history and who can use it, hand-over to the people and teams that can request the item (`GET deployments/N/hand_over/`), deletion after a confirmation, and a failed teardown with what it left; Approvals lists the requests waiting for the user, oldest first, each with its rule and condition, the requester's reason, the answers the condition reads highlighted, the quota and the timeout, and approves, or denies with a comment, from a bar at the bottom of a phone's screen (`/api/v2/portal/approvals/`); the mails link to the approval or the request in the portal and never act by themselves ([The portal](operations.md#the-portal)). AWX's approvals are a list in the admin UI, with no portal.
- Requests from another catalog (roadmap M15-10): a catalog such as ServiceNow requests items through the API with a user's token, follows the request (`catalog_requests/N/`) and reads the deployment's outputs, secrets masked; the item's `notification_templates_requests` get a webhook for each change of a request's state (`waiting`, `approved`, `denied`, `running`, `ready`, `done`, `failed`, `canceled`, `expiring`, `deleted`) with the request and its deployment, in order and once each, recorded with the change itself; the operator guide has a ServiceNow catalog item as the example ([Requests from another catalog](operations.md#requests-from-another-catalog)). AWX has no catalog; its job notifications cover started, success and error.
- Catalog items in the admin UI (roadmap M15-11): a Portal section in the navigation (catalog items, requests, deployments, catalog quotas and a link to the portal); a template's admins publish it from its page or from the list, in a form in sections: the item, its questions from the survey (reworded, hidden, narrowed, filtered, a default or a fixed answer shown or not), approval rules, the freeze exception team and the email notification, the deployment (its name, teardown, a lifetime kept until deleted or that expires, with extensions, how to connect and actions), quotas and step labels, with the API's errors on their fields; an item's page has its details, requests, notifications (request webhooks and expiry reminders) and access; the requests and deployments lists filter by item and status and link to the portal and the job ([In the admin UI](operations.md#in-the-admin-ui)). AWX has no catalog.
- Windows, sequences and absence in event rules (roadmap M14-07): per key, a count of events within a sliding window, all of several CEL conditions in any order, a sequence of them in order, and an event not followed by another, which fires from a timer at the window's end; the action gets every matched event as `events`; windows kept in PostgreSQL (`event_rule_patterns`), locked per key and committed with the decisions, so a restart or a failover keeps them and the rule's streams share them; windows counted by the time each event was received, a late event `expired`; shadow mode's windows apart, guardrails and approval applied when a window fires, one firing per window for the circuit breaker; the window's progress in each decision ("2 of 3 events"), the open windows on the rule's page and at `event_rules/N/patterns/`, and patterns in the editor, backtests and `awxnext rules test`. ansible-rulebook's rulebooks have `all`, `any`, `not` and timed conditions in memory, lost on a restart ([Patterns](operations.md#patterns)).
- Checks of fixes (roadmap M14-08): per rule, after each action, a wait for the event that resolves its key (the alert resolved) within a time after the action finished, or a check template launched with the action's variables and limit whose result, or `fixed` artifact, decides; outcomes `fixed`, `not_fixed` and `action_failed` per key, kept in PostgreSQL (`event_rule_checks`) so a restart or a failover keeps them; a fix that didn't work notifies, makes the key's next action wait for approval, and counts toward the circuit breaker; in shadow mode, whether keys resolve by themselves; a success rate per rule through the API (`success_rate`, `event_rules/N/checks/`), the metric `awxnext_event_rule_checks_total` and the UI, on each decision and job, in backtests and `awxnext rules test`. EDA's controller and ansible-rulebook record whether an action ran, not whether it fixed anything ([Checking fixes](operations.md#checking-fixes)).
- Rulebooks imported (roadmap M14-09): ansible-rulebook 1.3's rulebooks, from a project's `extensions/eda/rulebooks/` and `rulebooks/` at each sync (where EDA's controller looks for them) or uploaded to `/api/v2/rulebooks/`, translated into event streams (`webhook`, `alertmanager`), connectors (the other sources) and rules: conditions as CEL, with ansible-rulebook's semantics for missing attributes; `throttle`, `all`, `any`, `not_all` and `timeout` as M14-07's patterns; `match_multiple_rules`; `run_job_template` and `run_workflow_template` as launches with `job_args`, `ansible_eda`, `retries`, `delay`, `post_events` and `set_facts`, the template looked up by name and organization; `post_event` and `set_fact` as posted events; `debug` and `print_event` in the decision log (`log`). A report per rulebook, in the API and on the rulebook's page, gives each source, rule and action translated or not with the reason, and the notes where awxnext behaves otherwise; what has no faithful equivalent (facts kept across events, joins between a rule's events, `run_playbook`, `run_module`, `shutdown`, `retract_fact`) is reported, not approximated. Imported objects start disabled and in shadow mode, follow their rulebook at each import, keep what operators set, and refuse hand edits of translated fields. Tested on every example rulebook of ansible-rulebook 1.3.2 and ansible.eda 2.13.0, and against ansible-rulebook itself on an Alertmanager rulebook. EDA's controller runs rulebooks in `ansible-rulebook` activations, without a report ([Importing rulebooks](operations.md#importing-rulebooks)).
- EDA's API for the `ansible.eda` collection (roadmap M14-10): `/api/eda/v1/` over awxnext's objects, with EDA's fields, filters, pagination, errors and RBAC: organizations, teams, users, roles and their assignments, credential types, credentials and input sources, decision environments (execution environments), projects with sync, a proxy and `verify_ssl`, rulebooks and their sources, event streams with EDA's UUID, receiver path and `additional_data_headers`, controller tokens, and activations: a copy of a project's rulebook with its own connectors and rules, enabled (rules in `auto` mode as the user who enabled it), disabled, restarted (also on a project update), copied, its sources mapped to existing streams, its status from its connectors. - A collection hub (roadmap M13-01): Galaxy's v3 API under `/api/galaxy/`, in galaxy_ng's URLs and its older clients' paths, so `ansible-galaxy` and `ansible-builder` install, download and list versions from it unchanged, with Pulp's pagination and highest version; collections in namespaces that organizations own (`/api/v2/collection_namespaces/`, `CollectionNamespace Admin` and `Read` roles), visible as awxnext's RBAC allows and `404` to anyone else; personal tokens as `Authorization: Token` or `Bearer`; artifacts in the database, S3 or Azure Blob Storage (`HUB_STORAGE_*`); a managed Collection Hub Galaxy credential with which a job's requirements install gets a read token of its own, revoked when the install ends. - Publishing to the collection hub (roadmap M13-02): `ansible-galaxy collection publish` unchanged, its upload and import polling in galaxy_ng's shape (`v3/artifacts/collections/`, `v3/imports/collections/<id>/`), with an import log of each check: the client's SHA-256, a tarball read in memory with no member outside the collection and size and member limits (`HUB_MAX_UPLOAD_SIZE`), `MANIFEST.json` and `FILES.json` checksums, metadata, the namespace and the uploader's permission, no duplicate version; uploads land in `staging` (or `published` with the namespace's `auto_approve`), and approvers move them to `published` or `rejected` with galaxy_ng's `move` or `/api/v2/collection_versions/<id>/approve/` and `reject/`; `CollectionNamespace Upload` and `Approve` roles beside Admin (the owner) and Read, staging and rejected read by curators only; deprecation as galaxy_ng's `PATCH`; deletion of a version or a collection unless it is the only one meeting a project's requirement or a published dependency (`used_by`); `/api/v2/collections/`, `collection_versions/` and `collection_imports/`. galaxy_ng answers deprecation, moves and deletions with tasks; awxnext does them at once ([Publishing a collection](operations.md#publishing-a-collection)).
- Signing the collection hub's versions (roadmap M13-03): approval (and an `auto_approve` upload) signs `MANIFEST.json` with awxnext's own GPG key, generated on first use and wrapped by the master key; the signatures in a version's v3 detail in galaxy_ng's shape (`signatures`: `signature`, `pubkey_fingerprint`, `signing_service`, `pulp_created`), so `ansible-galaxy collection install --keyring --required-valid-signature-count` and `collection verify` check them unchanged; the public keys at `/api/galaxy/keyring.asc` and `keyring.gpg`; signatures made elsewhere uploaded by approvers on `/api/v2/collection_versions/<id>/signatures/`, checked against the version and recorded with the key's fingerprint and the uploader; key rotation on `/api/v2/collection_signing_keys/` (the new key signs from then on, the old one's signatures stay until it is deleted); a project's `collection_signature_validation_credential` and `collection_signature_count`, with which each job's requirements install requires that many valid signatures from a GPG Public Key credential's keys. AWX has no hub, and its projects check only their own files' ansible-sign signature; galaxy_ng's Pulp signature upload and signing-service API aren't served ([Signing collections](operations.md#signing-collections)).
- Mirroring collections from other servers (roadmap M13-04): remotes (`/api/v2/collection_remotes/`) of galaxy.ansible.com, Red Hat's Automation Hub (its offline token exchanged at its SSO server, as `ansible-galaxy` does) or another galaxy_ng, each with a `requirements.yml` of collections and version ranges, their dependencies at the highest version in range, and its own repository, read by its organization's members and jobs through a managed credential; each sync a `collection_sync` job (`/api/v2/collection_syncs/`) with its output and status, started by hand, scheduled and notified as a project update, through the remote's proxy, refusing local addresses unless listed in `HUB_REMOTE_ALLOWED_LOCAL_ADDRESSES`; additive (a version once mirrored stays unless the signature check below takes it out, a rebuilt one upstream fails the sync); the servers' signatures mirrored with the versions, unchecked or only those a GPG Public Key credential's keys verify, a version without one skipped and listed, and a range left with none failing the sync; `awxnext hub import` of a directory `ansible-galaxy collection download` wrote, with signatures in `.asc` files or `requirements.yml`.
