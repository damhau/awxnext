# awxnext

An AWX-compatible automation controller: a Go server with AWX's `/api/v2`, PostgreSQL, and a
React/Vite/TypeScript UI. AWX's clients (the `awx` CLI, the `awx.awx` collection, the Terraform
provider) must keep working against it.

## Layout

- `cmd/awxnext`: the server and its commands. `cmd/awxbench`, `cmd/gendocs` and
  `cmd/awxnext-jobexec` are tools and helpers.
- `internal/`: the server's packages. Database migrations are in `internal/db/migrations`,
  numbered `NNNN_name.sql`, one more than the last.
- `test/`: Go integration tests against an in-process server and a real PostgreSQL.
  - `test/kind` runs against the Helm chart in kind (CI only).
  - `test/isolation` runs against the Compose image (CI only).
- `ui/`: the web UI. Its logic lives in `ui/src/lib/*.ts`, with a Vitest test next to each file.
- `compat/`: AWX's own client test suites, run against a throwaway stack (`compat/run.py`).
- `deploy/`: Compose and the Helm chart. `docs/` holds the operator guide, the configuration
  reference, the parity table and the roadmap.

## Tests

Run the tests of what you changed, and nothing else: CI runs the rest on push.

- **Go code:** `make test` (vet and `go test -short ./...`, about 30 s), then the full tests
  of the area you changed: `go test ./test/ -run 'TestArea'`, without `-short`.
- **UI (`ui/`):** `cd ui && npx tsc --noEmit -p . && npx vitest run`, then check the page in
  the browser (below).
- **The Helm chart:** `helm lint deploy/helm/awxnext`, and `helm template` with the values you
  changed. `helm.yml` installs it in kind on push.
- **Workflows, Compose, docs:** check that the file parses; there is nothing to run locally.
  A workflow is tested by its first run. A new setting or environment variable is Go code:
  `make test` checks `docs/configuration.md` and `config.Vars`.
- **Before a milestone closes:** `gh workflow run full.yml` and `gh workflow run security.yml`.
  Both also run nightly. full.yml runs every Go test with the race detector, the chart and
  image tests, and the compat suites; `make test-full` is the local Go part of it. A manual
  security.yml run also builds and scans both images and uploads their SBOMs (the image job
  does not run on push); `make vuln` is its local equivalent.

Writing and running Go tests:

- **Slow tests:** mark a test that takes seconds with `slow(t)`. A test that runs jobs with
  ansible-runner calls `requireAnsible(t)`, which also counts as slow. Both keep the test out of
  the short suite. CI's short job has no ansible-runner, so an unmarked job test fails there.
- **PostgreSQL:** the tests use `AWXNEXT_TEST_DATABASE_URL`, as CI does, or else start a
  throwaway PostgreSQL 16. The first run downloads its binaries from Maven Central
  (repo1.maven.org) into `~/.cache/awxnext/embedded-postgres`; later runs need no network.
- **Running everything locally:** job tests need `ansible-runner` on the PATH; the object
  storage tests need `AWXNEXT_TEST_S3_*` and `AWXNEXT_TEST_AZURITE_BLOB_ENDPOINT` (see
  `test/archive_storage_test.go`).

CI and the browser:

- **CI on push:**
  - `ci.yml` runs on every push that changes more than docs, `.gitignore` or `LICENSE`, and on
    every PR: the short suite and the UI. On main, it then publishes the all-in-one image as
    `main-<commit time>-<commit>`. Argo CD Image Updater deploys that image to the permanent
    instance (the `awxnext` app in damhau/k8s-argocd), so a green push to main goes live.
  - `helm.yml` (the chart in kind) runs when the chart, the Dockerfile or the agent change;
    `compose.yml` (the image with Compose) when Compose, the Dockerfile or the job helper do.
  - `security.yml` (known vulnerabilities: govulncheck, `npm audit`) runs on a push to main
    that changes Go code, `go.mod`, `go.sum` or the UI's package files. A vulnerability with a
    fix fails it: upgrade the dependency (docs/operations.md, "Security scanning").
- **Checking the UI in a browser:** use the compat stack at http://localhost:8053
  (`admin` / `compat`), started with the UI override:

  ```sh
  (cd ui && npm run build)
  docker compose -f compat/docker-compose.yml -f compat/docker-compose.ui.yml up -d --build --wait
  ```

  After a UI-only change, run `npm run build` and reload the page. Rebuild the stack only when
  Go code changed. Its database is recreated on each rebuild, so sign in again.

## Rules

- Run `gofmt -l .` on the whole tree before committing; CI fails on any unformatted file.
- `docs/configuration.md` and `ui/src/lib/settings.generated.json` are generated by
  `go run ./cmd/gendocs` from the settings definitions and `internal/config/vars.go`. When you
  add a setting or an environment variable, regenerate them. Add each new variable to
  `config.Vars`: a test checks that every variable the code reads is listed. Place each new
  setting in `ui/src/lib/settingsLayout.ts`: the layout's test fails until it is placed.
- A feature comes with tests, docs, and its row in `docs/parity.md`. When a compat target starts
  passing, remove it from `compat/known-failures.yml`.
- The roadmap is `docs/ROADMAP.md`, tracked on GitHub as milestones and issues. Keep the two in
  sync.
- New dependencies, Go or images, pin an exact version; the latest stable release is fine.
  For Python, use `uv`.

## Git

- Commit on `main`, with no Claude or co-author trailers.
- `main` has no branch protection: pushes, the owner's and Claude Code's, go straight to it,
  and each green push deploys. Dependabot opens PRs, which the owner merges.
- Stage explicit paths, never `git add -A`. The dotfiles at the root (`.bashrc`, `.claude/`,
  `.idea`, `.mcp.json`, `.playwright-mcp/`...) are not part of the project; `.gitignore` lists
  them.
